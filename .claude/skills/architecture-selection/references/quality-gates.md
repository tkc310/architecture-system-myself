# 品質ゲート

この文書は、型、契約、副作用の分離、抽象化、テスト、リンターで機械に保証させる項目と、CI の基準を並べる。機械が保証した項目は、人間のレビューで見直さなくてよい。レビュー担当者は、要件との一致、業務ルールの正しさ、セキュリティに時間を使える。

## 機械に保証させる項目

| 保証したいこと | 手段 | 人間が見なくてよいこと |
| --- | --- | --- |
| 型の整合 | TypeScript の `strict` | 呼び出しの引数と戻り値の不一致 |
| 外部入力の形 | Zod のスキーマによる parse | 不正な入力が内部に入ること |
| 事前条件 | ブランド型（`Email`、`PositiveInt`） | 検証済みの値かどうか |
| 副作用の位置 | 依存ルール（L の場合、`domain/` から I/O を import しない） | 純粋関数が I/O を行っていないか |
| モジュール境界 | 依存ルール（公開 API 以外の import を禁止） | 内部実装への依存 |
| 振る舞い | テスト | 既存の振る舞いが壊れていないか |
| 書式と大きさ | フォーマッター、`max-lines` | 書式、ファイルの大きさ |

## 型

**必須**

- `tsconfig.json` で `strict` と `noUncheckedIndexedAccess` を有効にする。
- `any` を禁止する。型の分からない値は `unknown` で受け、スキーマで parse する。
- 型アサーションを禁止する。`as const` は使ってよい。外す箇所には、理由を書いたリンターの無効化コメントを付ける。

## 契約

**必須**

- 外部から入る値（HTTP のリクエスト、キューのメッセージ、環境変数、外部 API の応答）は、境界で Zod のスキーマにより parse する。型はスキーマから導出し（`z.infer`）、型とスキーマを別々に書かない。
- 事前条件は、parse した結果をブランド型にして表す。関数が `Email` を受け取るなら、呼び出し側は検証を済ませている。
  - 理由: 事前条件を型で表すと、関数の中で同じ検証を繰り返さずに済み、検証漏れは型チェックで見つかる。
- 事後条件は、戻り値の型（[CQS](./cqs.md) の結果型）とテストで表す。
- データベースのスキーマは、マイグレーションだけで変える。

**推奨**

- HTTP API の仕様（OpenAPI）は、スキーマから生成する。手で書いた仕様と実装を並行して保守しない。

## 副作用の分離と抽象化

**必須**

- 構造が L の場合、`domain/` は純粋関数と型だけにする。データベース、ネットワーク、ファイル、現在時刻、乱数に触れる処理は、引数で受け取るか `infrastructure/` に置く。
- 構造が L の場合、I/O は `ports.ts` のインターフェースを通す。ポートを置く場所と、それ以外にインターフェースを作らないことは [構造](./principles.md) の「間接化」に従う。
- 構造が S と M の場合、`domain/` と `ports.ts` を置かない。I/O は command / query から直接行い、共通処理は service に出す。詳細は [構造](./principles.md) の「間接化」に従う。

## テスト

**必須**

- 追加・変更したコマンドとクエリには、テストを付ける。層ごとのテストの書き方は [CQS](./cqs.md) に従う。
- テストの粒度、ツール選定、実行方針は [テスト戦略](./testing-strategy.md) に従う。
- カバレッジの閾値は、業務ロジックを含む層に設定する。L の場合は `domain/` と `application/`、S と M の場合は command / query / service とする。目安は行カバレッジ 80% とし、サービスごとの値を ARCHITECTURE.md に書く。
  - 理由: 全体の数値で縛ると、UI や生成コードのテストで数値を満たせてしまい、業務ルールのテスト不足を見逃す。

**推奨**

- E2E テストと VRT は実行コストが高いため、CI には含めずアドホックに手動実行できるようにする。詳細は [テスト戦略](./testing-strategy.md) を参照。

## リンターとフォーマッター

**必須**

- リンターとフォーマッターを使う。
- **Oxc エコシステムを優先的に採用する**:
  - リンター: **oxlint** を優先する。型情報を使う lint は **tsgolint**（oxlint の type-aware）を優先する。
  - フォーマッター: **oxfmt** を優先する。
  - 既存プロジェクトの事情や Oxc 未対応の要件がある場合のみ、他のツール（ESLint、Biome、Prettier など）を使う。
- **oxfmt のバージョン管理**:
  - oxfmt は 1.0 前（beta）で、0.x の minor 更新でも整形結果が変わる可能性がある。
  - バージョンを厳密に固定し（`package.json` で exact version）、更新は差分確認のうえでまとめて行う。
  - 全体整形コミットは `.git-blame-ignore-revs` に登録する。
- **Oxc エコシステムの他のツール**:
  - oxlint、oxfmt 以外の Oxc エコシステムのツール（例: oxc-parser、oxc-transform、Rolldown など）を採用する場合は、エージェントが自分で導入を決めず、採用するかどうかをユーザーに確認して判断を求める。
  - 確認時には、置き換える対象、安定性（stable/beta 等）、利点とリスクを簡潔に示す。
  - 理由: これらのツールは既存のビルドツールチェーンを大きく置き換える可能性があり、慎重な判断が必要。

**推奨**

- コミット前に、変更したファイルだけを lint-staged で検査する。ただし、`--no-verify` で回避できるので、CI の代わりにはならない。

**判断根拠**

2026-10 時点の根拠:

- oxlint v1.87 stable、ルール 871、type-aware lint は 2026-07 に stable（[出典](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)）
- oxfmt は JS/TS で Prettier 適合テスト 100%（[出典](https://oxc.rs/blog/2026-02-24-oxfmt-beta)）
- Vite+ 1.0 が oxlint/oxfmt を統合（[出典](https://voidzero.dev/posts/announcing-vite-plus-1-0)）
- 比較対象の Biome（v2.5）は単一ツールで安定だが、SCSS/YAML/Markdown の整形が未対応。これらの形式を扱わないプロジェクトでは選択肢になる
- oxc-parser、oxc-transform、Rolldown は、oxlint/oxfmt と違い既存のビルドツールチェーンを大きく置き換えうるため、採用はユーザーに確認する（上記の必須）

## 依存関係の管理

**必須**

- 依存関係（モジュール間・レイヤー間の import 方向、循環依存など）の管理が必要な場合は、dependency-cruiser を利用する。ルールは [構造](./principles.md) の依存の表から作る。
  - 理由: ESLint に依存しない単体 CLI なので、oxlint など ESLint 以外のリンターを使う構成でも使える。循環依存の検出や依存グラフの可視化ができる。
- 依存ルールの違反は、CI で検出してマージをブロックする。

## CI の必須ステージ

次をすべて通らない PR はマージしない。ブランチ保護で必須チェックに指定する。

1. フォーマットの確認
2. lint（dependency-cruiser による依存ルール、`max-lines` を含む）
3. 型チェック（`tsc --noEmit`）
4. テスト（ユニットと統合）とカバレッジの閾値
5. 生成コードの差分確認（生成を実行して `git diff --exit-code`）
6. ビルド

CI も手元と同じく `Makefile` のターゲットで叩く([規約](./coding-conventions.md#コマンドは-make-で叩く))。インストール(`make install`)は、その前に依存の供給網の設定(`.npmrc` の Takumi Guard と `pnpm-workspace.yaml` の `trustPolicy: no-downgrade`)が残っていることを確かめる([セキュリティ](./security.md#依存の供給網))。これはステージではなく、同じジョブの前処理にする。

**推奨**: 依存パッケージの脆弱性検査(`make audit`。Takumi Guard は取得専用なので、`--registry=https://registry.npmjs.org/` を付けている)。版の鮮度の確認(`make check-versions`)は、初期構築時と週次の見直しで行う。ネットワークの状態で結果が変わるので、マージを止める必須ステージには入れない。

## 人間のレビューで見る項目

- 変更が要件と一致しているか
- 業務ルール（計算、状態の遷移、権限）が正しいか
- 認証・認可、機密情報の扱い、入力の扱いに問題がないか
- モジュールの分け方と公開 API が、今後の変更に耐えるか
