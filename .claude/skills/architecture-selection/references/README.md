# アーキテクチャと技術選定のルール

このディレクトリには、新規サービスのアーキテクチャを設計し、技術スタックを選ぶためのルールを自然言語で置く。サービスの ARCHITECTURE.md を新規作成するとき、既存のものを調整するとき、既存のコードベースを評価・レビューするときに、AI エージェントと開発者が参照する。

前提は AI 駆動開発である。エージェントが一度に読む範囲を小さく保ち、人間のレビューを意図の確認に絞れる構造を選ぶ。

## どれを先に読むか

最初に [前提条件のヒアリング](./hearing.md) を行い、回答を確認してから、次の順でルールを適用する。

1. [構造の段階の選び方](./scale-selection.md)。開発人数、業務領域の数、業務ルールの複雑さから S / M / L を決める。
2. [技術選定](./tech-selection.md)。システムの性質からスタックを決める。第一候補はモジュラモノリスのフルスタック TypeScript である。性能の要件があれば [性能対策の段階](./performance-ladder.md) も、画面があれば [デザインシステムの選択](./design-system.md) も読む。
3. [構造](./principles.md) と [CQS](./cqs.md) のうち、採った段階の節。
4. [品質ゲート](./quality-gates.md) と [テスト戦略](./testing-strategy.md)。型、契約、テスト、リンターで機械に保証させる項目と、CI の基準を決める。
5. [編集制約](./editing-constraints.md)。エージェントが編集してよいパス、保護するパス、人間の承認が要る操作を決める。

文書どうしが食い違うときは、[承認](./human-approval.md) と [セキュリティ](./security.md) のルール、編集制約、品質ゲート、それ以外の文書の順で採る。

## ルールの強さ

各文書のルールには「必須」と「推奨」を付けている。

| ルール | ARCHITECTURE.md での扱い |
| --- | --- |
| [承認](./human-approval.md) と [セキュリティ](./security.md) のルール | 外せない。緩めることもできない |
| 各文書の必須 | 原則として採る。外すときは、外す理由を ARCHITECTURE.md の「外したルール」と ADR に書く |
| 推奨 | サービスごとに採るかどうかを決める |
| 「目安」と書いた数値 | 初期値である。サービスごとの値を ARCHITECTURE.md に書く |

## 収録内容

- [承認](./human-approval.md): 実行の前に人間の承認が要る操作と、要らない操作。最も優先する。
- [セキュリティ](./security.md): 秘密情報、外から入る文章、有害な出力の扱い。最も優先する。
- [前提条件のヒアリング](./hearing.md): 設計の前にユーザーに確認する項目と、聞き方。
- [構造の段階の選び方](./scale-selection.md): S / M / L の判定、段階による違い、昇格と降格の目安。
- [技術選定](./tech-selection.md): 既定のスタック、システムの性質ごとの判断表、TypeScript の中で性能を上げる段階、Go と Flutter を選ぶ条件、エラー処理の方針、Go のサービスへ切り出せる状態の保ち方。
- [性能対策の段階](./performance-ladder.md): Effect、Worker、WebAssembly、Go の順に進む手順と構成。
- [デザインシステムの選択](./design-system.md): 8341-ui を使わない、使う、8341-ui をひな形に作る、の選び方と取り込み方。
- [AI 駆動開発のための構造](./principles.md): 段階別のディレクトリ構成、公開 API、依存の向き、ファイルと関数の大きさ、命名、README と AGENTS.md。
- [ユースケース層の CQS](./cqs.md): 段階別のコマンドとクエリ、service、ポート、リードモデル、モジュール間イベント。
- [品質ゲート](./quality-gates.md): 機械に保証させる項目と手段、CI の必須ステージ、人間のレビューで見る項目。
- [テスト戦略](./testing-strategy.md): テストの粒度とツール、実行方針、AI 駆動開発における注意点。
- [コーディング規約](./coding-conventions.md): t_wada のコメント法則、コマンドは make で叩く、命名と行数。
- [編集制約](./editing-constraints.md): 作業の種類ごとの編集範囲、保護パス、承認が要る操作と、それを強制する仕組み。
- [出力の自己点検](./review-checklist.md): 出力を渡す前の確認項目。

## 作業ごとに読む文書

| 作業 | 読む文書 |
| --- | --- |
| ARCHITECTURE.md を新規作成する | すべて |
| スタックだけを決める | ヒアリング、技術選定、(性能の要件があれば)性能対策の段階、(画面があれば)デザインシステムの選択 |
| モジュールやユースケースを追加する | 採った段階の構造と CQS |
| CI やリンターを設定する | 品質ゲート、テスト戦略、採った段階の依存ルール |
| コマンドを足す、CI やフックの手順を書く | コーディング規約(コマンドは make で叩く) |
| エージェントのガードレールを設定する | 編集制約 |
| コードレビューやコミットメッセージを書く | コーディング規約 |

エージェントには、作業に合う文書だけをコンテキストに入れる。すべてを一度に渡す必要はない。

## 注意事項

- ライブラリ名は例である。採用するときに、最新のリリースと保守状況を公式の情報で確かめる。
- 採用する版は、サービスの ARCHITECTURE.md に書く。このディレクトリに書く版は、動作の下限と、判断根拠の時点の版だけにする。
