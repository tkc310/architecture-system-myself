# アーキタイプ定義と判定フロー

規模ではなく**業務ルールの複雑さと領域の数**で決める。画面数やテーブル数が多くても、ルールが単純なら L1 のままでよい。

## 判定フロー

```
Q1. 業務ルールは入力検証と単純な読み書きだけで済むか?
    ├─ はい → Q2 へ
    └─ いいえ(状態遷移・不変条件・計算・複数集約の整合性がある)→ Q3 へ

Q2. 独立して変化する業務領域が 3 つ以上、または開発者が 4 人以上か?
    ├─ いいえ → L1 crud-simple
    └─ はい  → L2 modular-monolith

Q3. ルールの多くが「1 つのモジュール内で閉じる」か?
    ├─ はい → L2 modular-monolith(必要なモジュールだけ domain/ を持つ)
    └─ いいえ、またはルールの正しさが事業上きわめて重要
               (金額、権利、法令、長期保守 3 年以上)→ L3 domain-centric
```

迷ったら下の段を選び、昇格条件を ADR に書く。

---

## L1: crud-simple(トランザクションスクリプト)

**形**:入口(Route Handler / Server Action / API ハンドラ)→ スキーマ検証 → DB クエリ → 応答。
**作らないもの**:ドメイン層、リポジトリ層、ユースケースクラス、DI コンテナ。

- 機能(feature)単位でファイルをまとめる。1 機能 = `schema.ts`(検証)、`actions.ts`(書き込み)、`queries.ts`(読み取り)、UI。
- DB アクセスは ORM のクエリビルダを直接呼ぶ。抽象化のためだけのラッパーを作らない。
- テストは主に統合テスト(本物の DB を使う)と E2E。純粋関数があればそこだけ単体テスト。

**境界ルール(機械で強制)**
- feature 同士は互いに import しない。共通化は `lib/` へ。
- UI コンポーネントは `db/` を直接 import しない(`queries.ts` / `actions.ts` 経由)。

**昇格条件(L2 へ)**
- 同じ業務ルールが 3 か所以上に重複した
- 業務領域が 3 つ以上になり、feature 間の参照を避けられなくなった
- DB なしでルールをテストしたい場面が繰り返し出てきた

---

## L2: modular-monolith(縦割りモジュール)

**形**:業務領域ごとのモジュール。各モジュールは `index.ts` だけを公開し、中身は自由。
**原則**:モジュール内は L1 と同じ単純さから始め、ルールが育ったモジュールにだけ `domain/` を足す。

- モジュール = 業務領域(会員、注文、請求…)。技術の層で分けない。
- モジュールは自分のテーブルを所有する。他モジュールのテーブルを直接読まない(公開関数を呼ぶ)。
- モジュール間連携は「公開関数の呼び出し」か「ドメインイベント(同一プロセス内)」。
- 共通の型・ユーティリティは `shared/` に置き、業務ロジックは置かない。

**境界ルール(機械で強制)**
- 他モジュールは `modules/<name>/index.ts` 経由でのみ import できる。
- モジュール間の循環依存を禁止。
- `shared/` は `modules/` を import しない。

**昇格条件(L3 へ)**
- 1 つのモジュールで不変条件の破れ(不整合データ)がバグとして繰り返し出た
- 外部システム(決済、在庫、他社 API)の差し替え・複数実装が必要になった
- 正しさの検証に、DB を使わない網羅的な単体テストが必要になった

**降格の検討**:モジュールが 2 つ以下に減った場合は L1 に戻してよい。

---

## L3: domain-centric(ヘキサゴナル/クリーン、モジュール単位)

**形**:L2 のモジュールの内側を、domain / application / infrastructure / presentation に分ける。**全モジュールに強制しない**。ルールの重いモジュールにだけ適用し、他は L2 の形のまま。

- `domain/`:エンティティ、値オブジェクト、ドメインエラー、純粋関数。フレームワーク・DB・HTTP を知らない。
- `application/`:ユースケース。必要な外部依存を「ポート(インターフェース)」として宣言する。
- `infrastructure/`:ポートの実装(DB リポジトリ、外部 API クライアント)。
- `presentation/`:HTTP ハンドラ / Server Action。application だけを呼ぶ。
- 依存性注入と型付きエラーには Effect(`Context` / `Layer`、`Effect` のエラー型)を推奨。使わない場合は関数引数で依存を渡す。

**境界ルール(機械で強制)**
- domain → (shared-kernel 以外)どこにも依存しない
- application → domain のみ
- infrastructure → application, domain
- presentation → application(domain の型参照は可)
- 他モジュールへは `index.ts` 経由のみ(L2 と同じ)

**降格の検討**:domain/ が薄い(ロジックがゲッター/セッターだけ)モジュールは L2 の形に戻す。

---

## 修飾子

アーキタイプとは独立に付け加える。必要なものだけ ADR に書く。

| 修飾子 | 既定の選択 | 置き場所 |
|--------|------------|----------|
| performance | `performance-ladder.md` の段で決める | 段による |
| realtime | WebSocket / SSE。まず SSE を検討。サーバーレス制約があればマネージドサービス | `src/realtime/` または該当モジュール |
| background-jobs | DB をキューにする方式(Postgres ベースのジョブキュー)から始め、量が増えたら専用キュー | `src/jobs/`、ジョブは各モジュールの公開関数を呼ぶだけ |
| multi-tenant | 行レベル分離(tenant_id + Postgres RLS)を既定。強い隔離要件のみスキーマ/DB 分離 | `db/` とミドルウェア |
| public-api | OpenAPI を契約の正とし、型を生成 | `contracts/` |
