# 技術選定

この文書は、新規サービスの技術スタックを、システムの性質から選ぶ基準を並べる。第一候補はモジュラモノリスのフルスタック TypeScript である。性能の要件をこれで満たせないと分かったときは、まず [TypeScript の中で性能を上げる段階](#typescript-の中で性能を上げる段階) を試し、それでも足りないときにサーバー側では Go を検討する。モバイルの UI では Flutter を検討する。

## 既定のスタック

**必須**

- 言語は TypeScript、構成はモジュラモノリス（一つのリポジトリ、一つのデプロイ単位、モジュールに分けたコード）とする。
  - 理由: フロントエンドとバックエンドで型とスキーマを共有でき、エージェントが扱う言語とツールが一種類で済む。デプロイ単位が一つなら、サービス間通信の失敗や分散トランザクションを扱わなくてよい。
- データベースは PostgreSQL とする。

**推奨**（選んだものと理由を ARCHITECTURE.md に書く）

| 用途 | 候補 | 理由 |
| --- | --- | --- |
| Web とフルスタック | Next.js（App Router） | SSR と静的生成、API を一つのアプリにまとめられる |
| SEO の要らない SPA | Vite と React Router | サーバーを持たない構成にできる。React Router v7 は Remix の機能を引き継いでいる |
| API を分ける場合 | Hono、Fastify | 依存が少なく、スキーマ検証と組み合わせやすい |
| DB アクセス | Drizzle、Prisma、Kysely | 型付きのクエリを書ける |
| 検証 | Zod | スキーマから型を導出できる |
| デザインシステム | 8341-ui を使わない / 使う / 作る | 画面があるときに選ぶ。[デザインシステムの選択](./design-system.md) |
| テスト | Vitest、Testing Library、Playwright | ユニットから E2E まで TypeScript で書ける |
| ジョブ | BullMQ | Redis でキューと再試行を扱える |
| I/O の並行処理 | Effect | Fiber による構造化された並行処理で、並行数の上限、タイムアウト、キャンセル、再試行を型付きで書ける。[性能対策の段階](./performance-ladder.md) の段階 2 に進んだときだけ採用する |
| エラー処理 | neverthrow | 期待される失敗を型で表現できる（採用時） |

## 既定から外れる条件

**必須**

- 既定から外れるのは、次のどちらかを示せるときに限る。
  - 負荷試験やプロファイリングで、既定のスタックが要件を満たさない箇所を特定した。
  - 要件の性質上、既定のスタックでは実現できない（ネイティブアプリが必須、など）。
- 外れる範囲は、要件を満たさない箇所（一つのモジュール、一つのクライアント）に限る。サービス全体を置き換えない。
- 外れた理由と測定の結果を ARCHITECTURE.md に書く。

## システムの性質ごとの判断

数値は目安である。判断の根拠は、この数値ではなく測定の結果とする。Node.js でも、処理の軽い I/O 中心の API なら、1 プロセスで毎秒 1 万件を超えることがある。

| 性質 | 既定での対応 | 他を検討する条件 |
| --- | --- | --- |
| トラフィック | 水平スケール、キャッシュ、CDN | 台数を増やしても費用や応答時間が要件に合わないと測定で分かった → [段階](#typescript-の中で性能を上げる段階) を試し、足りなければ該当モジュールを Go に |
| 応答時間 | DB のインデックス、キャッシュ | p99 の要件を満たせない原因が Node.js の実行時間だと分かった → 該当処理を Worker か WebAssembly に移し、足りなければ該当モジュールを Go に |
| CPU を長く使う処理 | ジョブに分けて非同期にする | イベントループを止める処理が常にある → Worker、次に WebAssembly、それでも足りなければ Go のワーカーに |
| リアルタイム | WebSocket か SSE | 音声・映像の配信 → 専用のメディアサーバーかマネージドサービス |
| オフライン・モバイル | PWA | ネイティブアプリが必須 → Flutter か React Native（下記） |
| データの一貫性 | コマンドごとのトランザクション | 結果整合性を許容できる高負荷の読み込み → [CQS](./cqs.md) の完全な CQRS |
| 決済・規制 | 監査ログ、暗号化、権限の検査を必須にする | 規制が実行環境を指定する → 指定に従う |
| チーム規模 | 1 チームで 1 つのモジュラモノリス | 独立してリリースしたいチームが複数ある → 該当モジュールの切り出し |
| SEO | Next.js の SSR か静的生成 | SEO が不要 → SPA |
| 機械学習の推論 | マネージドの推論サービスを API で呼ぶ | 自前で運用する → Python（FastAPI など）の別サービス |

## TypeScript の中で性能を上げる段階

**必須**

- 性能の要件を満たせないと測定で分かったら、Go を検討する前に、次の段階を上から順に試す。各段階に進む根拠（測定の結果）を ARCHITECTURE.md に書く。
  - 理由: 言語とツールチェーンを一種類に保てば、型とスキーマの共有、エージェントが扱う範囲の小ささ、デプロイ単位の少なさを失わずに済む。

| 段階 | 対象のボトルネック | 手段 |
| --- | --- | --- |
| 1. 基本の対策 | すべて | インデックス、N+1 の解消、キャッシュ、ジョブへの分離 |
| 2. I/O の並行処理 | 外部 API や DB の待ち、多数の同時接続 | Effect の Fiber で並行数を制御する。Fiber は一つのスレッドで動く軽量な並行処理であり、CPU を複数コアで使うものではない |
| 3. CPU の並列処理 | イベントループを止める CPU 処理 | `worker_threads`（Effect の Worker、Piscina など）に移す |
| 4. WebAssembly | Worker に移しても遅い計算の中心部分 | Rust（wasm-bindgen）などで書いた純粋な計算関数を WebAssembly にして TypeScript から呼ぶ。I/O と業務ルールは TypeScript に残す |
| 5. Go | 上の段階で要件を満たせない、または運用上の理由がある | 次の節に従い、該当モジュールだけを切り出す |

各段階の手順と構成は [性能対策の段階](./performance-ladder.md) を参照する。

**推奨**

- WebAssembly にした関数には、TypeScript の実装と結果が一致するかを確かめるテストと、ベンチマークを置く。
- 段階 4 と 5 は、ビルドの工程と保守する言語が増えるので、エージェントが自分で決めず、ユーザーに確認する。

## Go を選ぶとき

**必須**

- Go は、測定で特定したモジュールの切り出し先として使う。[TypeScript の中で性能を上げる段階](#typescript-の中で性能を上げる段階) の 1〜4 で要件を満たせないことを、測定で示してから選ぶ。最初からサービス全体を Go にするのは、チームが Go を主に使っていて、フロントエンドを持たない場合に限る。
- TypeScript との境界は OpenAPI で定義し、双方の型を生成する（openapi-typescript、oapi-codegen など）。

**推奨**

- ルーティングは標準の `net/http` から始める（Go 1.22 以降は、メソッドとパスのパターンで振り分けられる）。ミドルウェアが増えたら chi や Echo を検討する。
- DB アクセスは sqlc と pgx にする。SQL から型付きのコードを生成でき、ORM の振る舞いを追わなくて済む。

## Flutter を選ぶとき

**必須**

- Flutter は、ネイティブアプリが提供価値の中心で、iOS と Android で同じ独自の UI とアニメーションを保ちたいときに選ぶ。Flutter は自前のレンダラー（iOS と Android の既定は Impeller）で描画するので、OS ごとの見た目の差が出にくい。
- チームが TypeScript だけで、UI が OS 標準の部品で足りるなら、React Native（Expo）か PWA を先に検討する。

**推奨**

- 状態管理は Riverpod か Bloc、オフラインのデータは drift（SQLite）にする。Isar と Hive の元のパッケージは保守が止まっているので、新規には選ばない。

## エラー処理の方針

構造が L のサービスでは、期待される失敗を型で表現するため、neverthrow の採用を検討する。ヒアリングで採用を決めたサービスのみ、次の方針に従う。

**必須**

- バックエンドの use-case 層（[CQS](./cqs.md) のコマンドとクエリ）では、`Result` / `ResultAsync` で期待される失敗を返す。
- フロントエンドでは、エラー処理が本質的に必要な箇所だけに使う。データ取得、検証（Zod の `safeParse` 結果をラップ）、外部 API 呼び出しなど。UI コード全体には広げない。
- 予期しない失敗（バグ、システム障害）は、これまで通り throw する。

**推奨**

- `Result` の未処理を検出する ESLint ルールを設定する。元の `eslint-plugin-neverthrow` はメンテされていないため、ESLint v9 以降では `@ninoseki/eslint-plugin-neverthrow` のような互換フォーク版を使う。

**注意**

neverthrow はメンテナンス頻度が低い（2025年2月以降リリースなし、2026年10月時点）。代替ライブラリ（byethrow、unthrown など）も存在する。採用する場合は、この状況を承知のうえで選択すること。

## Go のサービスへ切り出せる状態を保つ

モジュールを後で Go のサービスに切り出すとき、障害になるのは共有されたテーブル、共有されたトランザクション、言語に依存した公開 API である。

**必須**

- 構造が M と L の場合、各モジュールは自分のテーブルだけを読み書きする。他モジュールのテーブルへの JOIN と外部キーを作らない。テーブル名にはモジュールの接頭辞を付けるか、モジュールごとにスキーマを分ける。
- 構造が S の場合、書き込みは自分の feature が所有するテーブルに限る。query 内の JOIN と集計は [構造](./principles.md#query-の-join-と集計) に従う。
- 公開 API の入出力は、Zod のスキーマを持つプレーンなデータにする。クラスのインスタンス、関数、ORM のエンティティを渡さない。
  - 理由: スキーマのあるプレーンなデータなら、関数呼び出しを HTTP の呼び出しに置き換えても契約が変わらない。

**推奨**

- 切り出し候補のモジュールでは、他モジュールとトランザクションを共有しない。L の場合、モジュールをまたぐ整合は、[CQS](./cqs.md) のドメインイベントとアウトボックスで取る。
