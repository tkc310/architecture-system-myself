# 構造の段階の選び方

構造は 3 段階から選ぶ。決め手は画面数やテーブル数ではなく、**開発人数**、**独立した業務領域の数**、**業務ルールの複雑さと変更頻度**である。要件を満たす中で最も単純な段階を選ぶ。

| 段階 | 形 | 層 | 向いている案件 |
| --- | --- | --- | --- |
| S: slice | `features/` の Vertical Slice + CQS | なし。command / query から ORM を直接使う | 1〜2 人、CRUD 中心、仕様変更が少ない |
| M: modular | `modules/` + 公開 API + テーブルの所有 | なし。S と同じく ORM を直接使う | 3 人以上、または独立した業務領域が 3 つ以上。ただし業務ルールは単純 |
| L: layered | `modules/` + `domain/` / `application/` / `infrastructure/` | あり。軽量 DDD | 4 人以上 かつ 複雑なドメインロジック かつ 仕様変更が頻繁 |

## 判定

**必須**

1. 次を**すべて**満たすなら **L**。
   - 4 人以上で開発する
   - 単純な CRUD ではなく、複雑なドメインロジック（状態遷移、不変条件、計算）を含む
   - 仕様変更が頻繁に発生する
2. L でなく、次の**どちらか**に当たるなら **M**。
   - 3 人以上で開発する
   - 独立して変化する業務領域（会員、請求、在庫など）が 3 つ以上ある
3. どちらでもなければ **S**。

- 判定に使った回答と、選んだ段階を ARCHITECTURE.md と ADR に書く。
- 境界上にあり、どちらも同程度に妥当なときは、ユーザーに確認する。回答が得られないときは単純な方を選び、昇格の条件を ADR に書く。
  - 理由: 層は後から足せるが、使われない層を外す変更は影響範囲が広い。

## 段階による違い

| 項目 | S | M | L |
| --- | --- | --- | --- |
| 最上位の単位 | `features/<feature>/` | `modules/<module>/` | `modules/<module>/` |
| 公開 API（`index.ts`） | query と service | query と service | command、query、入出力の型 |
| 他の単位の command を呼ぶ | 不可（`app/` からだけ） | 不可（`app/` からだけ） | 可（公開された command） |
| テーブル | 書き込みは自分の feature が所有するテーブルだけ。query の JOIN は可 | 自分のモジュールのテーブルだけを読み書きする。他モジュールへの JOIN と外部キーは作らない | M と同じ |
| テーブル定義の置き場所 | `shared/db/schema/` | `modules/<module>/tables.ts` | `modules/<module>/infrastructure/tables.ts` |
| ポートと DI | なし | なし | `ports.ts` とコンポジションルート |
| モジュールごとの `AGENTS.md` | 不要 | 必須 | 必須 |
| エラー処理 | 判別可能なユニオン | 判別可能なユニオン | neverthrow を検討（[技術選定](./tech-selection.md#エラー処理の方針)） |
| 依存ルール | `templates/harness/dependency-cruiser/slice.cjs` | `modular.cjs` | `layered.cjs` |

M でテーブルの所有を必須にするのは、複数人が並行して変更しても影響範囲がモジュールに収まり、後で [Go のサービスへ切り出せる状態](./tech-selection.md#go-のサービスへ切り出せる状態を保つ) を保てるからである。

## 段階の変更

**必須**

- 段階を変えるときは、新しい ADR を書き、ARCHITECTURE.md の変更履歴に残す。

**昇格の目安**

| 変更 | 目安 |
| --- | --- |
| S → M | 開発者が 3 人以上になった。feature 間の query の JOIN が増え、どの feature がどのテーブルを変えるか追えなくなった |
| M → L（モジュール単位） | あるモジュールで、不変条件の破れによるバグが繰り返し出た。同じ業務ルールが 3 か所以上に重複した。DB を使わずにルールを網羅的に検証したくなった |

- M から L への昇格は、**ルールの重いモジュールだけ** を L の形にしてよい。L の依存ルールは `domain/` などのディレクトリを持つモジュールにだけ効くので、軽いモジュールは M の形のまま残せる。

**降格の目安**

| 変更 | 目安 |
| --- | --- |
| L → M（モジュール単位） | `domain/` の中身がゲッターと単純な検証だけになっている |
| M → S | 開発者が 2 人以下になり、業務領域も 2 つ以下に減った |
