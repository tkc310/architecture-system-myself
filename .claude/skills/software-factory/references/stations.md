# 工程

ソフトウェアファクトリーは、一つの変更を次の 7 つの工程に通す。各工程は**入力**と**出力**が決まっており、出力が次の工程の入力になる。工程の間で受け渡すのは会話ではなくリポジトリ内のファイルなので、エージェントが入れ替わっても、人が途中から入っても続きを追える。

| # | 工程 | 担当 | 入力 | 出力 | 通過の条件 |
| --- | --- | --- | --- | --- | --- |
| 1 | 仕様化 | `planner` エージェント + 人 | Issue、依頼 | `docs/specs/NNNN-<slug>.md`(状態: 草案) | 準備完了の定義を満たす |
| 2 | 計画 | `planner` エージェント | 仕様 | 仕様の「計画」節(作業の分割、編集範囲、テスト計画) | 人が仕様と計画を承認する(状態: 承認) |
| 3 | 実装 | `implementer` エージェント | 承認済みの仕様 | ブランチ上のコミット | 受け入れ条件ごとのテストがある |
| 4 | 検証 | フックと CI | コミット | `pnpm check` の結果 | 品質ゲートの必須ステージがすべて通る |
| 5 | 独立レビュー | `reviewer` エージェント(手元の `/review`)+ GitHub 側のレビュー(形式 A: GitHub Actions、形式 B: ルーティン) | 仕様と差分だけ | 指摘(必須 / 推奨)と、ステータス `factory/review` | 必須の指摘がなく、`factory/review` が成功 |
| 6 | 振り返り | `retro` エージェント | PR、レビューの指摘、この PR での CI の失敗 | 同じ PR に含める `docs/feedback/LESSONS.md` への追記 | 誤りがあれば記録した |
| 7 | マージ | 人 | PR | main へのマージ | 必須チェック(品質ゲート、`secrets-scan`、`factory/review`)、CODEOWNERS、人の承認がそろう |

週に一度、改善の工程が工場全体を見直す([改善ループ](./improvement-loop.md))。

## 準備完了の定義(工程 1 → 3 に進む条件)

**必須**

- 受け入れ条件が、テストに書き下せる形(前提 / 操作 / 結果)で列挙されている。
- 影響するモジュール(S では feature)と、編集してよい範囲が書かれている。範囲は [編集制約](../../architecture-selection/references/editing-constraints.md) の作業の種類に合わせる。
- 承認が要る操作(マイグレーション、依存の追加、保護パスの編集など)が洗い出されている。
- 未解決の質問がない。
- 人が承認し、仕様の状態が「承認」になっている。
  - 理由: エージェントは曖昧な仕様を推測で埋める。推測を実装の前に止めれば、手戻りが最も小さい。

## 完了の定義(工程 7 に進む条件)

**必須**

- `pnpm check` が通る。
- 受け入れ条件の一つひとつに、対応するテストがある。PR の説明で対応を示す。
- `reviewer` エージェントの必須の指摘がない。
- 仕様の範囲外の変更がない。範囲外の変更が要るなら、仕様を更新して承認を取り直す。
- PR テンプレートの項目が埋まっている。
- 振り返りを済ませ、記録があれば同じ PR に含めた。
  - 理由: 記録だけの PR を別に作らずに済み、誤りの記録とその原因の差分が一緒にレビューされる。

## 工程を省いてよい場合

**推奨**

- 1 ファイル程度の修正(誤字、設定値の変更、依存の更新)は、仕様を書かずに Issue と PR の説明で代える。工程 3〜7 は省かない。
- 調査だけの作業は、工程 1 の出力を `docs/specs/` ではなく Issue のコメントにしてよい。

## 仕様の状態

| 状態 | 意味 | 変えてよい人 |
| --- | --- | --- |
| 草案 | 作成中。未解決の質問がある | エージェント、人 |
| 承認 | 準備完了の定義を満たし、人が承認した。実装してよい | 人だけ |
| 実装済み | PR がマージされた。PR の中で状態を変えておく | エージェント、人 |
| 取り下げ | 実装しない。理由を書く | 人だけ |

承認済みの仕様の受け入れ条件と編集範囲は、エージェントが書き換えない。変える必要が出たら、作業を止めて人に確認する。
