# ユースケース層の CQS

この文書は、ユースケース層のハンドラーを、コマンドとクエリに分けるルールを並べる。コマンドは状態を変え、ドメインのデータを返さない。クエリは状態を変えず、データを返す。分けておくと、ハンドラーの名前と置き場所だけで副作用の有無が分かり、レビューで確認する観点もハンドラーの種類ごとに決まる。

構造の段階（[構造の段階の選び方](./scale-selection.md)）により、適用するルールが異なる。

- **S と M** → [S と M の CQS](#s-と-m-の-cqs) を読む。Command と Query の基本的な分離、service の役割、feature / モジュール間の呼び出し方を定める。domain 層と infrastructure 層は作らず、Command と Query から ORM を直接使う。
- **L** → [L の CQS](#l-の-cqs) を読む。ポートと依存の注入、リードモデルと CQRS、モジュール間のイベントを扱う。

UI のイベントハンドラーと純粋関数は、この文書の対象ではない。

## S と M の CQS

Command と Query の基本的な分離と、service を通じた共通処理の切り出しに集中する。domain 層と infrastructure 層は作らず、Command と Query から ORM を直接使う。M では `features/` を `modules/` と読み替える。

### Command

**必須**

- 一つのファイルに一つの command を置く（`commands/place-order.command.ts`）。入力型、ハンドラー関数、結果型を同じファイルに書く。
- 入力は一つのオブジェクトで受け取り、Zod のスキーマで検証する。
- 戻り値は、作成・更新した対象の ID（必要なら楽観ロック用のバージョン）か、想定内の失敗を表す判別可能なユニオンにする。ドメインのデータ（エンティティや一覧）は返さない。画面が更新後の値を必要とするときは、command の後に query を呼ぶ。

```ts
type PlaceOrderResult =
  | { ok: true; orderId: OrderId }
  | { ok: false; reason: "out_of_stock" | "credit_limit_exceeded" };
```

- 在庫切れのような業務上の失敗は結果型で返し、DB の接続断のような想定外の失敗は例外にする。
  - 理由: 想定内の失敗を型に含めると、呼び出し側が処理し忘れたときに型チェックで検出できる。
- 一つの command が一つのトランザクションを持つ。書き込むテーブルは、自分の feature が所有するものに限る（[技術選定](./tech-selection.md) の切り出しの条件）。M では読み取りも自分のモジュールのテーブルに限る（[構造](./principles.md#テーブルの所有)）。
- Command から直接 ORM を使ってよい。

### Query

**必須**

- 一つのファイルに一つの query を置く（`queries/get-order.query.ts`）。
- 戻り値は画面や呼び出し側が使う形の型にする。ORM のエンティティをそのまま返さない。
- 該当がないときは、単一の取得なら `null`、一覧なら空配列を返す。
- Query から直接 ORM を使ってよい。

### Service

**必須**

- Service は名詞（集合やルール）単位で切り出す。例: `stock.service.ts`、`pricing.service.ts`。
- ルールや計算は、2回目に現れたときに service に抽出する。
- Service は、他の feature から呼べる共通処理として公開できる。

### Feature / モジュール間の呼び出し

**必須**

- 他の feature のデータは、その feature の `index.ts` が公開する query で読む。
- 他の feature の共通処理は、公開された service を呼ぶ。
- 他の feature の command は呼ばない。Command は `app/` からだけ呼ぶ。
  - 理由: command の副作用が連鎖して追いにくくなるのを防ぐ。

## L の CQS

ポートによる I/O の抽象化、依存の注入、リードモデル、モジュール間のイベントを扱う。

### Command

**必須**

- 一つのファイルに一つのコマンドを置く（`commands/place-order.command.ts`）。入力型、ハンドラー関数、結果型を同じファイルに書く。
- 入力は一つのオブジェクトで受け取り、Zod のスキーマで検証する。
- 戻り値は、作成・更新した対象の ID（必要なら楽観ロック用のバージョン）か、想定内の失敗を表す判別可能なユニオンにする。ドメインのデータ（エンティティや一覧）は返さない。画面が更新後の値を必要とするときは、コマンドの後にクエリを呼ぶ。

```ts
type PlaceOrderResult =
  | { ok: true; orderId: OrderId }
  | { ok: false; reason: "out_of_stock" | "credit_limit_exceeded" };
```

- 在庫切れのような業務上の失敗は結果型で返し、DB の接続断のような想定外の失敗は例外にする。neverthrow を採用したサービスでは、結果型を `Result` / `ResultAsync` で表す（[エラー処理の方針](./tech-selection.md#エラー処理の方針)）。
  - 理由: 想定内の失敗を型に含めると、呼び出し側が処理し忘れたときに型チェックで検出できる。
- 一つのコマンドが一つのトランザクションを持つ。書き込むテーブルは、自分のモジュールが所有するものに限る（[技術選定](./tech-selection.md) の切り出しの条件）。

### Query

**必須**

- 一つのファイルに一つのクエリを置く（`queries/get-order.query.ts`）。
- クエリのハンドラーは、読み取り専用のポートだけを引数で受け取る。書き込みメソッドを持つポートを渡さない。
  - 理由: クエリが書き込まないことを、レビューではなく型で保証できる。
- 戻り値は画面や呼び出し側が使う形の型にする。ORM のエンティティをそのまま返さない。
- 該当がないときは、単一の取得なら `null`、一覧なら空配列を返す。

### ポートと依存の渡し方

**必須**

- `ports.ts` で、読み取りと書き込みのインターフェースを分ける（`OrderReader` と `OrderWriter`）。コマンドは両方を、クエリは読み取りだけを受け取る。
- 依存（ポート、時刻、ID の生成）はハンドラーの引数で受け取る。DB クライアントなどの実体を、ハンドラーの中で生成したり直接 import したりしない。
  - 理由: テストでインメモリ実装に差し替えられ、ハンドラーが触れる I/O を引数の型から読み取れる。

```ts
export async function placeOrder(
  deps: { orders: OrderWriter; stock: StockReader; now: () => Date },
  input: PlaceOrderInput,
): Promise<PlaceOrderResult> { /* ... */ }
```

**推奨**

- 依存の組み立ては `app/` の一か所（コンポジションルート、`src/app/composition-root.ts`）で行う。DI コンテナは使わない。ここだけが各モジュールの `infrastructure/` を import してよい（[構造](./principles.md#依存の向き) の依存ルール）。
  - 理由: 依存の解決が一つのファイルで読め、間接化が増えない。

### テスト

**必須**

- `domain/` の関数は、モックなしで入力と出力を検証する。
- コマンドとクエリは、ポートのインメモリ実装を渡して検証する。コマンドでは書き込まれた内容と結果型を、クエリでは返す値を確認する。
- `infrastructure/` のポート実装は、実際のデータベースに対して統合テストを行う。

**推奨**

- `domain/` の不変条件（合計金額が負にならない、など）は、fast-check によるプロパティベーステストで検証する。

### リードモデルと CQRS

既定は、書き込みと読み込みが同じデータベースを使う軽量な構成である。クエリは、画面に合わせた SQL やビューを使ってよい。

**必須**

- クエリ専用のテーブルやビュー（リードモデル）は、クエリだけが読む。コマンドの判断に使わない。
- マテリアライズドビューは、更新（`REFRESH`）までの古さを許容できる画面にだけ使う。更新直後の値が要る画面には、通常のビューか、書き込みと同じトランザクションで更新するテーブルを使う。

**推奨**

- 読み込み用のデータストアを分ける完全な CQRS は、次の三つがそろうときに検討する。読み込みの負荷が書き込みより桁違いに大きいこと、通常の SQL では応答時間の要件を満たせないと測定で分かったこと、読み込み側の遅延（結果整合性）を利用者が許容できること。イベントソーシングは CQRS の前提ではなく、別の判断として扱う。

### モジュール間の呼び出し

**必須**

- 他のモジュールのデータは、そのモジュールの `index.ts` が公開するクエリで読む。状態の変更は、公開されたコマンドを呼ぶ。他モジュールのテーブルやポート実装に直接触れない。
- 既定は同期の関数呼び出しとする。

**推奨**

- 呼び出し元が結果を待つ必要のない副作用（注文確定後の通知、監査ログ）は、プロセス内のドメインイベントで分けてよい。イベントの中身はスキーマ付きのプレーンなデータにし、購読側の処理は発行側のトランザクションのコミット後に実行する。
  - 理由: コミット前に通知を送ると、ロールバックされた注文の通知が届く。
- イベントの取りこぼしが許されないときは、イベントを同じトランザクションでテーブルに書き、別の処理が配信する（トランザクショナルアウトボックス）。
