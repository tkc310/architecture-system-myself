# ユースケース層の CQS

この文書は、ユースケース層のハンドラーを、コマンドとクエリに分けるルールを並べる。コマンドは状態を変え、ドメインのデータを返さない。クエリは状態を変えず、データを返す。分けておくと、ハンドラーの名前と置き場所だけで副作用の有無が分かり、レビューで確認する観点もハンドラーの種類ごとに決まる。

構造の段階([構造の段階の選び方](./scale-selection.md))により、適用するルールが異なる。

- **S と M** → [S と M の CQS](#s-と-m-の-cqs) を読む。command と query の基本的な分離を定める。
- **L** → S と M の command と query のルールを前提に、[L の CQS](#l-の-cqs) の差分を読む。ポートと依存の注入、リードモデルと CQRS、モジュール間のイベントを扱う。

UI のイベントハンドラーと純粋関数は、この文書の対象ではない。

## S と M の CQS

domain 層と infrastructure 層は作らず、command と query から ORM を直接使う。M では `features/` を `modules/`、feature をモジュールと読み替える。

### Command

**必須**

- 一つのファイルに一つの command を置く(`commands/place-order.command.ts`)。入力型、ハンドラー関数、結果型を同じファイルに書く。
- 入力は一つのオブジェクトで受け取り、Zod のスキーマで検証する。
- 戻り値は、作成・更新した対象の ID(必要なら楽観ロック用のバージョン)か、想定内の失敗を表す判別可能なユニオンにする。ドメインのデータ(エンティティや一覧)は返さない。画面が更新後の値を必要とするときは、command の後に query を呼ぶ。

```ts
type PlaceOrderResult =
  | { ok: true; orderId: OrderId }
  | { ok: false; reason: "out_of_stock" | "credit_limit_exceeded" };
```

- 在庫切れのような業務上の失敗は結果型で返し、DB の接続断のような想定外の失敗は例外にする。
  - 理由: 想定内の失敗を型に含めると、呼び出し側が処理し忘れたときに型チェックで検出できる。
- 一つの command が一つのトランザクションを持つ。書き込むテーブルは、自分の feature が所有するものに限る([Go のサービスへ切り出せる状態を保つ](./tech-selection.md#go-のサービスへ切り出せる状態を保つ))。M では読み取りも自分のモジュールのテーブルに限る([構造](./principles.md#テーブルの所有))。

### Query

**必須**

- 一つのファイルに一つの query を置く(`queries/get-order.query.ts`)。
- 戻り値は画面や呼び出し側が使う形の型にする。ORM のエンティティをそのまま返さない。
- 該当がないときは、単一の取得なら `null`、一覧なら空配列を返す。

### Service と feature 間の呼び出し

service の切り出し方と、feature 間で呼べるもの(service と query だけ。command は `app/` からだけ呼ぶ)は、[構造](./principles.md#service-の切り出し) と [公開 API](./principles.md#公開-api) に従う。

## L の CQS

S と M の [Command](#command) と [Query](#query) のルール(ファイルの単位、入力の検証、戻り値、結果型、トランザクション)はそのまま適用する。違いは次のとおり。

### Command と Query の差分

**必須**

- command と query は ORM を直接使わず、`ports.ts` のポートを通す(下の「ポートと依存の渡し方」)。
- neverthrow を採用したサービスでは、結果型を `Result` / `ResultAsync` で表す([エラー処理の方針](./tech-selection.md#エラー処理の方針))。
- query のハンドラーは、読み取り専用のポートだけを引数で受け取る。書き込みのメソッドを持つポートを渡さない。
  - 理由: query が書き込まないことを、レビューではなく型で保証できる。

### ポートと依存の渡し方

**必須**

- `ports.ts` で、読み取りと書き込みのインターフェースを分ける(`OrderReader` と `OrderWriter`)。command は両方を、query は読み取りだけを受け取る。
- 依存(ポート、時刻、ID の生成)はハンドラーの引数で受け取る。DB クライアントなどの実体を、ハンドラーの中で生成したり直接 import したりしない。
  - 理由: テストでインメモリ実装に差し替えられ、ハンドラーが触れる I/O を引数の型から読み取れる。

```ts
export async function placeOrder(
  deps: { orders: OrderWriter; stock: StockReader; now: () => Date },
  input: PlaceOrderInput,
): Promise<PlaceOrderResult> { /* ... */ }
```

**推奨**

- 依存の組み立ては `app/` の一か所(コンポジションルート、`src/app/composition-root.ts`)で行う。DI コンテナは使わない。ここだけが各モジュールの `infrastructure/` を import してよい([構造](./principles.md#依存の向き) の依存ルール)。
  - 理由: 依存の解決が一つのファイルで読め、間接化が増えない。

### テスト

**必須**

- `domain/` の関数は、モックなしで入力と出力を検証する。
- command と query は、ポートのインメモリ実装を渡して検証する。command では書き込まれた内容と結果型を、query では返す値を確認する。
- `infrastructure/` のポート実装は、実際のデータベースに対して統合テストを行う。

**推奨**

- `domain/` の不変条件(合計金額が負にならない、など)は、fast-check によるプロパティベーステストで検証する。

### リードモデルと CQRS

既定は、書き込みと読み込みが同じデータベースを使う軽量な構成である。query は、画面に合わせた SQL やビューを使ってよい。

**必須**

- query 専用のテーブルやビュー(リードモデル)は、query だけが読む。command の判断に使わない。
- マテリアライズドビューは、更新(`REFRESH`)までの古さを許容できる画面にだけ使う。更新直後の値が要る画面には、通常のビューか、書き込みと同じトランザクションで更新するテーブルを使う。

**推奨**

- 読み込み用のデータストアを分ける完全な CQRS は、次の三つがそろうときに検討する。読み込みの負荷が書き込みより桁違いに大きいこと、通常の SQL では応答時間の要件を満たせないと測定で分かったこと、読み込み側の遅延(結果整合性)を利用者が許容できること。イベントソーシングは CQRS の前提ではなく、別の判断として扱う。

### モジュール間の呼び出し

**必須**

- 他のモジュールのデータは、そのモジュールの `index.ts` が公開する query で読む。状態の変更は、公開された command を呼ぶ。他モジュールのテーブルやポート実装に直接触れない。
- 既定は同期の関数呼び出しとする。

**推奨**

- 呼び出し元が結果を待つ必要のない副作用(注文確定後の通知、監査ログ)は、プロセス内のドメインイベントで分けてよい。イベントの中身はスキーマ付きのプレーンなデータにし、購読側の処理は発行側のトランザクションのコミット後に実行する。
  - 理由: コミット前に通知を送ると、ロールバックされた注文の通知が届く。
- イベントの取りこぼしが許されないときは、イベントを同じトランザクションでテーブルに書き、別の処理が配信する(トランザクショナルアウトボックス)。
