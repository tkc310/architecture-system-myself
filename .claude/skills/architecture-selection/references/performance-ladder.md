# 性能エスカレーションの段(P0〜P4)

**下の段から順に検討し、計測で不足が確認できたときだけ上がる。** 各段は前の段を置き換えず、積み重ねる。P2 以上は必ず ADR を書き、P3 以上は採用前にユーザーに確認する。

## まずボトルネックの種類を見分ける

| 症状 | 種類 | 効く段 |
|------|------|--------|
| 外部 API・DB 待ちが長い、同時接続が多い | I/O 待ち | P0, P1 |
| CPU 使用率が 100% に張り付く、イベントループが止まる | CPU 処理 | P0, P2, P3 |
| メモリ・GC 停止が問題、長時間動く大量並行処理 | 実行環境の特性 | P2, P4 |

> 注意:Effect の Fiber は**同じスレッド上の軽量な並行処理**であり、CPU を複数コアで並列に使うものではない。CPU 処理の高速化には P2(Worker)か P3(WebAssembly)が必要。

---

## P0: 計測と基本対策(常に最初)
- 計測:OpenTelemetry でトレース、DB のスロークエリログ、負荷試験(k6 など)。
- 対策:N+1 解消、インデックス、ページング、キャッシュ(HTTP キャッシュ、CDN、メモ化)、不要なシリアライズの削減。
- **ここで解決する案件が大半**。P1 以上へ進むには計測結果を ADR に添付する。

## P1: I/O 並行性を Effect で扱う
- 用途:多数の外部呼び出しの並行実行、タイムアウト・リトライ・キャンセル、流量制御、ストリーム処理。
- 使うもの:Effect の Fiber による構造化並行性、並行数の上限指定、`Stream`(背圧付き)、`Schedule`(リトライ)、`Semaphore`。
- 構成への影響:該当するモジュールの application 層(L1 なら actions)で Effect を使う。全体を Effect 化する必要はない。

## P2: CPU 並列(Worker)と実行環境
- 用途:画像処理、集計、パースなど CPU を使う処理でイベントループを止めたくないとき。
- 使うもの:Node.js の `worker_threads`(Effect の Worker 機能、または Piscina などのプール)。重い処理はジョブキューへ逃がすことも検討する。
- 実行環境:Node.js LTS を既定とし、起動速度などで差が出る場合のみ Bun を比較検討する。
- 構成:`src/workers/` に Worker 入口を置き、呼び出しは型付きのメッセージ契約(スキーマ)で行う。

## P3: WebAssembly でホットパスだけ置き換える
- 用途:P2 でも足りない CPU 処理の中心部分(数値計算、圧縮、暗号、パーサ等)。
- 使うもの:Rust + wasm-bindgen(wasm-pack)を既定。TS に近い書き味を優先するなら AssemblyScript。
- 原則:
  - WebAssembly は**純粋な計算関数**に限る。I/O や業務ルールは TS 側に残す。
  - TS 側に薄いラッパー(`packages/wasm-<name>/`)を置き、外からは普通の TS 関数に見せる。
  - 同じ入力に対し TS 実装と結果が一致するテスト(差分テスト)とベンチマークを置く。
- 採用前にユーザー確認:ビルド工程と保守言語が増えるため。

## P4: Go サービスへ切り出す(最後の手段)
- 採用条件(**いずれか**を計測で示せること):
  - 持続的な CPU 処理の量が P2/P3 では運用コストに見合わない
  - 大量の長時間並行処理で Node.js のメモリ・GC が要件を満たさない
  - 単一バイナリ配布など、運用上の明確な要求がある
- 原則:
  - 切り出すのは**境界の明確な 1 つの機能**だけ。業務ロジック全体を Go に移さない。
  - 契約(OpenAPI または Protocol Buffers / Connect)を正とし、TS 側の型を生成する。手書きの型を作らない。
  - Go 側もハーネスを持つ:`gofumpt`、`golangci-lint`、`go test -race`、契約テスト。
- 構成:`services/<name>/`(Go)、`contracts/`(契約)、生成した TS クライアントは `packages/contracts/`。
- 採用前にユーザー確認。
