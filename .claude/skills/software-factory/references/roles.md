# エージェントの役割

工程ごとに役割を分けたエージェント(Claude Code のサブエージェント)を置く。役割を分けるのは、**読むものと触れるものを工程ごとに絞る**ためである。一つのエージェントがすべてを行うと、コンテキストが膨らみ、自分の実装を自分で甘く採点する。

| 役割 | 工程 | 読むもの | 使えるツール | 書いてよいもの |
| --- | --- | --- | --- | --- |
| `planner` | 仕様化、計画 | Issue、ARCHITECTURE.md、ADR、関係するモジュールの README と AGENTS.md と `index.ts` | 読み取り(Read、Grep、Glob)、`docs/specs/` への書き込み | `docs/specs/` だけ |
| `implementer` | 実装 | 承認済みの仕様、編集範囲のファイル | 読み書き、Bash(許可リストの範囲) | 仕様の編集範囲だけ |
| `reviewer` | 独立レビュー | 仕様と差分だけ。実装の経緯や会話は渡さない | 読み取りと、検査コマンドの実行 | 書かない |
| `retro` | 振り返り、改善 | PR、レビューの指摘、CI の失敗、LESSONS.md | 読み取り、`gh` の読み取り系コマンド、`docs/feedback/` への書き込み | `docs/feedback/` だけ |

## 役割のルール

**必須**

- `reviewer` は、`implementer` と別のコンテキストで動かす。渡すのは仕様と差分だけにする。
  - 理由: 実装の経緯を知っていると、意図を補って読んでしまい、仕様と差分の食い違いを見落とす。
- `reviewer` には、ファイルを書き換えるツール(Edit、Write)を与えない。
- `planner` と `retro` の書き込み先は、役割の定義で `docs/specs/` と `docs/feedback/` に限る。ツールではパスを絞れないので、範囲外の書き込みは CI のレビューが仕様の編集範囲との照合で見つける。
- 役割の定義ファイル(`.claude/agents/*.md`)は保護パスにする。エージェントが自分の権限を広げられないようにする。
- 役割ごとに、読む文書を明示する。すべての文書を読ませない。

**推奨**

- `reviewer` には、`implementer` より慎重に推論するモデルや設定を使う。
- 指摘は「必須」と「推奨」に分けて出させる。必須は、仕様との不一致、品質ゲートでは検出できない境界違反、セキュリティ、承認の要る操作の見落としに限る。

## 人の役割

| 場面 | 人が行うこと |
| --- | --- |
| 工程 2 の後 | 仕様と計画を承認する。受け入れ条件が要件どおりかを見る |
| 工程 7 | 要件との一致、業務ルールの正しさ、セキュリティを見てマージする。機械が保証した項目は見直さない |
| 承認が要る操作 | 実行の前に承認する |
| 週次の改善 | 改善の PR を読み、採るルールを決める |
