# 前提条件のヒアリング

このスキルを使う作業では、設計や技術選定の案を出す前に、前提条件をユーザーに確認する。新規作成、既存の調整、評価・レビューのどの作業モードでも、これを最初の手順とする。

## ヒアリング項目

### 既存の情報の確認

リポジトリ内で確認できる情報を先に調べる。

- 既存の ARCHITECTURE.md の有無と内容
- 言語、フレームワーク、データベース(パッケージ定義、設定ファイル、マイグレーション)
- デプロイ先とコンテナの有無(`Dockerfile`、IaC、CI の設定)
- モバイルアプリの有無(`ios/`、`android/`、Flutter や React Native の設定)
- チームの規模(CODEOWNERS、コミット履歴)

### ユーザーへの質問項目

リポジトリから推測できない項目だけを質問する。短いリストにまとめる。

#### 1. サービスとユーザー

- **目的**: 誰の、どの作業を支えるサービスか
- **利用者**: 一般の個人、契約組織、社内のいずれか。想定する人数

#### 2. 負荷と性能

- **トラフィック**: 平常時とピーク時のリクエスト数の見込み
- **応答時間**: 主要な操作で許容できる待ち時間
- **重い処理**: 画像・動画の変換、大量の集計、機械学習の推論があるか
- **同時実行**: 外部 API や DB を多数並行して呼ぶ処理、多数の同時接続があるか([性能対策の段階](./performance-ladder.md) の判断に使う)

#### 3. 機能の性質

- **リアルタイム性**: 他の利用者の操作を即座に反映する画面があるか
- **オフラインとモバイル**: ネイティブアプリが要るか。通信のない状態で使うか
- **SEO**: 検索エンジンからの流入が要るか
- **画面とデザインシステム**: 画面があるか。あれば、デザインシステムをどう扱うか([デザインシステムの選択](./design-system.md))
  - A. 8341-ui を使わない(組織の既存のデザインシステムがあれば、その名前)
  - B. 8341-ui を使う
  - C. 8341-ui をひな形に、デザインシステムを作って複数のプロダクトで共有する(ブランドのキーカラー)
  - D. 8341-ui の色調などを変えて、このプロダクトだけの部品として組み込む(キーカラー、中立色、書体。リポジトリもワークスペースも作らない)

#### 4. データと規制

- **一貫性**: 更新の直後に、すべての画面で同じ値が見える必要があるか
- **お金と個人情報**: 決済、個人情報、医療情報を扱うか
- **規制**: 準拠が要る法令や基準(個人情報保護法、GDPR、PCI DSS など)

#### 5. チームと制約

- **開発人数**: 何人で開発・保守するか
- **業務領域の数**: 独立して変化する業務領域(会員、請求、在庫など)はいくつあるか
- **アプリケーションの性質**:
  - **CRUD 中心か**: 主に作成、読み取り、更新、削除の操作で構成されるか
  - **業務ルールの複雑さ**: 状態遷移、不変条件、計算などの複雑な業務ルールを含むか
  - **仕様変更の頻度**: 仕様変更が頻繁に発生するか
- **期限と予算**: リリースの期限、運用費の上限
- **エラー処理**: 構造が L になりそうな場合、`neverthrow`(`Result` / `ResultAsync`)を使ったエラー処理を採用するか。詳細は [エラー処理の方針](./tech-selection.md#エラー処理の方針) を参照

開発人数、業務領域の数、アプリケーションの性質の回答から、[構造の段階の選び方](./scale-selection.md) で S / M / L を決める。

#### 6. 既存の環境

- **連携**: 接続が要る既存システム、API、データベース
- **ホスティング**: 決まっているクラウドや実行環境

## ヒアリングの進め方

### 質問の構成

1. **既存情報の要約**: リポジトリから推測できた内容を示す
2. **確認が必要な項目**: 推測できない項目だけを質問する
3. **回答の確認**: 回答を要約し、理解が正しいか確認してから設計に進む

### 質問の例

```
リポジトリを確認したところ、Next.js と PostgreSQL の構成で、ARCHITECTURE.md はありませんでした。
次の点を確認させてください。

1. 利用者: 社内向けですか、契約した組織向けですか。想定する人数はどのくらいですか
2. 重い処理: 画像変換や大量の集計など、CPU を長く使う処理はありますか
3. モバイル: ネイティブアプリは必要ですか
4. 体制: 何人で開発しますか。独立した業務領域(会員、請求など)はいくつありますか
5. 業務ルール: 状態遷移や計算などの複雑なルールはありますか。仕様変更は頻繁ですか

期限や、決まっているホスティング先があれば教えてください。
```

## 回答の記録

回答は、サービスの ARCHITECTURE.md の「前提条件」に書く。書き方は [テンプレート](../templates/ARCHITECTURE.md) に従う。

## 注意事項

- 質問は一度にまとめて行う。後から追加で聞くことは避ける
- ユーザーが「分からない」と答えた項目は、既定値で進め、仮定として ARCHITECTURE.md に書く([SKILL.md](../SKILL.md) の進め方)。仮定を見直す条件(ピーク時の負荷が見込みを超えたら、など)も添える
- 前提条件が変わった場合は、ARCHITECTURE.md を更新する
