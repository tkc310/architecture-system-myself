# 改善ループ

工場は、自分の失敗から規則を足して良くなる。改善は二つの周期で回す。

| 周期 | 担当 | 入力 | 出力 |
| --- | --- | --- | --- |
| PR ごと | `retro` エージェント(`/retro`) | PR、レビューの指摘、その PR の CI の失敗 | 同じ PR に含める `docs/feedback/LESSONS.md` への追記 |
| 週ごと | 改善ジョブ(形式 A: `factory-improve.yml`、形式 B: ルーティン `factory-improve`) | 直近 1 週間の LESSONS.md の追記、CI の失敗、PR のレビューコメント | 規則を昇格させる下書き PR と、週次の報告 |

## PR ごとの振り返り

**必須**

- マージの前に、PR のブランチで `/retro <PR 番号>` を実行し、記録を同じ PR に含める。
- 記録するのは、**仕組みで防げたはずの誤り**だけにする。例: レビューで指摘された境界違反、CI で初めて見つかった型の抜け道、仕様にない変更、同じ質問の繰り返し。
- 既に同じ種類の記録があれば、新しい行を足さず回数を増やす。
  - 理由: 回数が昇格の判断材料になる。

## 週ごとの改善

**必須**

- 週に一度、改善ジョブを動かす。形式 A は `templates/github/workflows/factory-improve.yml`、形式 B は `templates/routines/weekly-improve.prompt.md` のルーティン。どちらも手動でも起動できる(Actions の workflow_dispatch、ルーティンの Run now)。
- 改善ジョブは次を集める。
  - LESSONS.md のうち、回数が 2 以上で、状態が「記録のみ」の行
  - 直近 1 週間に失敗した CI のジョブと、失敗したステップ(どの規則で落ちたか)
  - 直近 1 週間にマージされた PR のレビューコメントのうち、必須の指摘
- 集めたものから、昇格の候補を選び、規則を変更する**下書き PR**を作る。昇格の優先順位は LESSONS.md の運用ルールに従う(型 → 依存ルール → lint → テスト → フック → 文章)。
- PR の説明に週次の報告を書く: 集計の結果、選んだ候補と理由、選ばなかった候補と理由。
- 改善の PR は人がレビューしてマージする。改善ジョブは PR をマージしない。

## 自己改善の歯止め

改善ジョブとエージェントは、ガードレールを**強める**変更だけを提案できる。

**必須**

- 規則を緩める変更(lint ルールの無効化、依存ルールの例外、権限の許可の追加、保護パスの削除)は、改善ジョブが自分で提案しない。必要と判断したら、PR ではなく Issue で人に問う。
- ガードレールの設定ファイルは保護パスなので、改善の PR は CODEOWNERS の承認を必須にする。
- 一つの PR で変える規則は、一つの種類の誤りに対するものに限る。
  - 理由: 規則の効果と副作用を、誤りの種類ごとに追える。

## 規則の効き目の確認

**推奨**

- 昇格した規則には、その誤りを再現するファイルやテストを付け、規則が実際に止めることを示す(依存ルールなら違反する import、lint なら違反するコード)。
- 昇格から 4 週間、同じ種類の誤りが記録されないかを週次の報告で確認する。再発したら、規則の穴を記録する。

## スキル自体への還元

対象リポジトリで昇格した規則のうち、他の案件でも使えるものは、このスキルと architecture-selection の `FEEDBACK.md` に記録し、雛形に取り込む提案をする。
